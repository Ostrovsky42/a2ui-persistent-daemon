# A2UI P0: отзыв по живому прогону и план доработок

Дата: 2026-09-07. Статус: предложения для следующей итерации; реализация не выполнена.

Проверенный P0 commit: `5ea8aa99c28dd9f9db0fb9ea29ec5ec71b9aaa27`.
Документ добавлен в `feature/agent-cli-roundtrip`, куда ранее слит этот P0.

Связанные материалы: [подключение Codex](../../codex-mcp.md),

## Основание и границы отзыва

Источники — результаты MCP calls и сообщения пользователя в совместной сессии.
Настоящий Codex публиковал UI, пользователь работал в Bubble Tea, агент получал
semantic events и обновлял экран. Отдельная видеозапись и измерения задержек
не сохранялись. Агент не видел терминал непосредственно: предложения по визуальному
качеству не являются результатами визуального аудита.

На точном P0 commit локально прошли build, HTTP/IPC smoke, reattach, startup stress,
полные обычный и race suites, vet, staging install/uninstall. Использовался Go 1.26.3
на Linux; это не проверка минимального Go 1.24. Результаты зафиксированы в разговоре,
не отдельным CI run. Fuzz и performance benchmarks в этот прогон не входили.

## Что подтвердилось

- Codex обнаружил `a2ui_publish`, `a2ui_wait_event`, `a2ui_status`.
- Свежая session `default`: `nodes=1`, `revision=0`. После подключения
  `has_client=true`, но пользователь видел пустой экран до первой публикации.
- Таблица staging/production дала реальный `committed`, затем `select` с `row_id`.
  Ожидание с фильтром сохранило `committed` в `observed_events`.
- Получены четыре активации: staging, staging, production, production.
  Агент использовал последнее событие. Это правило демонстрации, а не согласованный
  контракт подтверждения; никакой деплой не запускался.
- После обновления: `has_client=true`, `pending_publish=false`, `revision=5`.
  Подтверждение публикации не является измерением скорости рендера.
- Опубликованы input и selectable table с 18 демонстрационными записями.
  Реальный `submit value="worker"` дал две строки: `billing-worker`, `image-worker`.
  Последующее обновление подтверждено клиентом. Полнота прокрутки и поведение
  на разных размерах терминала отдельно не проверялись.
- Ошибочный `progress.value=100` получил HTTP 422 (`value must be 0..1`). Ранние
  операции пакета уже применились; после исправления на `1` продолжение прошло.
  Один publish с несколькими операциями не является транзакцией.

## Комментарий тестера

Сильная сторона — рабочая поверхность, которая сохраняется между шагами агента.
Выбор приходит с устойчивым ID, и агент продолжает работу на том же экране.
Это полезная основа для форм, выбора и наблюдения за задачей.

Слабое место — предсказуемость. Пустой экран выглядел сломанным; поиск требовал
ожидания агента; после завершения его хода поле продолжало обещать новый поиск,
хотя активного ожидания событий уже не было. Отзыв пользователя:
«не слишком удобно, но уже неплохо».

Часть проблем относится к демонстрации: английский интерфейс в русском разговоре,
технический `row_id` в пользовательском тексте и progress 100% без выполняемой
операции. Корректная формулировка: «Выбрано: production. Деплой не запускался».
Кроме того, `text` в V1 добавляет содержимое, а не заменяет его. Демо применяло
его к заголовку как replace-операцию и накопило старые сообщения. Для замены
text-node нужен same-ID `upsert` с новыми props; append оставить для логов и stream.

## План по приоритетам

### 1. Понятный экран и состояние подключения

- [ ] Добавить host-local экран ожидания при пустом Document:
  «Клиент подключён. Ожидаем интерфейс от агента». Не создавать фиктивные agent
  nodes или publication acknowledgements.
- [ ] Показывать потерю связи. Статус «агент обрабатывает запрос» выводить только
  при соответствующем сигнале: `has_client` не доказывает, что агент ждёт события.
- [ ] Пересобрать демо: язык разговора, один заголовок, поиск, таблица, число
  результатов и клавиши. Убрать технические ID и ложный progress.
- [ ] Для нулевой выдачи показать запрос и способ сброса. Проверить существующий
  индикатор окна строк и улучшить его при необходимости; его отсутствие
  в текущем renderer не подтверждено.

Приёмка: пользователь различает ожидание контента и ошибку подключения, видит
фокус и способ сброса; понимает, что выбор окружения не запускает деплой.
Проверить пустой экран, 0/2/18 результатов и узкий терминал.

Предлагаемая композиция (эскиз, не снимок renderer):

```text
Развёртывания                              18 записей
Поиск: [ worker                         ]
Enter — применить · пустой запрос — показать все

Сервис                  Окружение       Состояние
› billing-worker        production      Работает
  image-worker          production      Работает

Найдено: 2 из 18
Tab — к таблице · ↑↓ — навигация · Enter — открыть
```

### 2. Поиск и жизненный цикл обработчика

- [ ] Исправить текущий сценарий: input + Enter, состояние обработки, результат
  и повторное ожидание. После остановки обслуживания явно обозначать это в UI.
- [ ] Проверить последовательные запросы, пустой запрос, нулевую выдачу, таймаут
  и возврат к списку. Сохранять исходные строки у владельца данных.
- [ ] Для загруженных строк спроектировать локальный поиск при вводе без LLM.
  До реализации определить владение запросом и связь input/table: в V1 нет
  `table.search`, нельзя молча добавить неизвестное свойство.
- [ ] Сохранить исходный Document и stable row IDs; определить фокус, выбор скрытой
  строки, сброс и обновление данных агентом. Проверить соответствие `row`/`row_id`
  существующему контракту, когда видимый список отфильтрован.

Приёмка: `worker` даёт 2 строки, пустой запрос — 18, неизвестный — 0. Повторный
поиск работает без сообщения в чат. Для будущего локального поиска ввод символа
не вызывает MCP/LLM, выбор возвращает правильный исходный `row_id`.

### 3. Однозначный выбор и повторные события

- [ ] Задать контракт сценария: просмотр строки, изменение выбора или однократное
  подтверждение. Не назначать последнее событие окончательным молча.
- [ ] Сразу показывать принятие Enter. Для однократного подтверждения завершать
  соответствующий шаг; повторные события не должны повторять действие.
- [ ] Проверять тип события, ID элемента, action и актуальность шага. Старые
  события оставлять для диагностики, не применять к новому экрану.
- [ ] Проверить быстрые Enter и смену строки между активациями. Несколько `select`
  не доказывают дефект: пользователь мог нажать Enter несколько раз.
  Debounce не заменяет идемпотентность действия.

Приёмка: согласованное правило однозначно определяет выбор; очередь событий
не вызывает повторное выполнение одного шага. Демо не запускает реальный деплой.

### 4. Публикация, понятная агенту

- [ ] Дополнить доступное агенту описание компонентов свойствами, диапазонами
  и примерами; явно описать `progress.value` как `0..1`.
- [ ] Явно разделить append `text` и замену содержимого text-node через same-ID
  `upsert`; добавить готовый шаблон обновления заголовка/статуса.
- [ ] Добавить раннюю проверку пакета с переиспользованием существующей валидации.
  Проверку формы/диапазонов не выдавать за транзакционность или защиту от всех
  ошибок, зависящих от текущего состояния.
- [ ] При частичном отказе сообщать индекс операции, подтверждённую применённую
  часть и способ продолжения. При неоднозначном транспортном сбое не утверждать,
  что операция точно не применена, и не советовать слепой повтор.
- [ ] Предоставить готовые композиции выбора, поиска и результата поверх V1.

Приёмка: неверный диапазон получает понятную ошибку; агент знает границу частичного
успеха, сохраняет sequence и завершает обновление после исправления.
`commit` остаётся publication barrier, не rollback/transaction control.

### 5. Подключение и восстановление

- [ ] Добавить preflight/doctor: бинарники, путь MCP, доступность daemon,
  ожидаемая/фактическая session, клиент и pending publication.
- [ ] Проверить запуск по абсолютному пути и дать короткий runbook без зависимости
  установленного пользователя от временного checkout.
- [ ] Ясно отличать переподключение terminal от рестарта MCP: P0 не восстанавливает
  mutation sequence после рестарта MCP. При несовпадении session диагностировать
  проблему до первой мутации.

Приёмка: проверить чистую конфигурацию, отсутствие daemon/клиента, неверную session
и рестарт MCP; пользователь получает конкретное действие для восстановления.

## Скорость: что измерить

The concrete prompts, data sets and exploratory baseline live in
[latency and visualization test cases](2026-09-07-a2ui-latency-and-visualization-test-cases.md).

Время tool call включает инфраструктуру выполнения и иногда ожидание человека;
по нему нельзя выделить скорость renderer. Нужны отдельные измерения:

- [ ] Клавиша → локальный redraw; publish → frame ACK; submit → получение агентом;
  submit → публикация ответа.
- [ ] p50/p95 на согласованных размерах терминала и объёмах таблицы; фиксировать
  версии Go/OS/terminal, размер окна, число строк и способ измерения.
- [ ] Синтетический ввод использовать с явной пометкой для автоматических замеров;
  мерцание, фокус и читаемость отдельно проверять вручную.

Ориентир для обсуждения: p95 локальной реакции на клавишу ≤ 100 мс на фиксированной
конфигурации. Это будущая цель, не измеренный результат. Допустимую задержку
агентского ответа определить после замеров; ожидание должно быть видимым.
Не оптимизировать renderer до установления места задержки.

## Порядок следующего прогона

Начать с пунктов 1–3: они исправляют непосредственно испытанные неудобства.
Сначала устойчивый повторный поиск через Enter, затем отдельное решение о локальном
поиске. Улучшения tools и установки выполнять следующими небольшими изменениями.
Базовые замеры скорости снять до оптимизаций.

Повторить Codex → Bubble Tea → человек → event → обновление UI. Зафиксировать commit,
версии, события и конечный status; с согласия пользователя добавить запись терминала.
После code changes выполнить проверки затронутого поведения и обязательные release
gates перед заявлением о готовности релиза. Этот отзыв не меняет прежние CI-статусы
и не расширяет обещания безопасности P0.
